# Internationalization

gvim's own strings are English, and the plugin API can translate plugin text. This
document records the i18n layer and its translation workflow: the `i18n` package, the
embedded catalogues, the Fresh import, validation/coverage and the Settings locale row.
The extracted inventory is small (25 English keys); the mapped subset ships translated
in all 15 Fresh locales, and the rest falls back to English by design.

## The i18n package

`i18n` is a TUI-free leaf package at the module top level (only the standard
library). It is imported by the app startup, the editor package (clipboard statuses), the
TUI root (a few notices) and the dock, and the plugin host reads the active locale from it.
The API:

```go
i18n.Locales() []i18n.Language   // the 15 Fresh locales, code + English + native name
i18n.Find(code) (Language, bool)
i18n.Normalize(tag) string       // env/config tag -> catalogue code
i18n.Resolve(configLocale, getenv) string
i18n.SetLocale(code); i18n.Locale() string
i18n.T(locale, key, vars) string        // translate, %{name} interpolation
i18n.TN(locale, key, n, vars) string    // plural form for n
i18n.PluralCategory(locale, n) string   // CLDR cardinal category
i18n.Register(locale, table)            // install/replace a catalogue (tests, callers)
i18n.ValidateCatalogue(locale, table) []error     // CI validation of one locale
i18n.ValidateCatalogueJSON(locale, data) []error  // same, from a raw file (duplicate keys too)
i18n.CoverageFor(locale) i18n.Coverage           // translated/total/missing report
i18n.FreshMap() map[string]string                 // gvim key -> Fresh key import table
```

`T` with an empty locale uses the active one. An unknown key comes back as the key
itself, so a missing translation is visible rather than empty.

## Catalogue layout and the Fresh import

The catalogues live in `i18n/locales/<locale>.json` and are embedded with
`//go:embed locales/*.json` (a few KB; a test caps the embedded text at 64 KiB so a
careless full import cannot bloat the binary silently). `i18n/locales/en.json` is the
**source of truth** and the only complete file; the other 14 files contain only the keys
gvim reuses from Fresh, so they are tiny and their coverage is explicit.

- Every extracted string has one key. Where the English wording/meaning matches Fresh's,
  the key is Fresh's (`clipboard.copied`, `terminal.no_terminal_open`, ...); a gvim-only
  string uses `gvim.<area>.<name>`.
- `i18n/fresh_map.json` is the explicit gvim-key → Fresh-key import table (13 entries:
  the clipboard/format/terminal keys, plus `gvim.scrollback.copied_line` →
  `clipboard.copied_line`, `gvim.scrollback.no_selection` → `clipboard.no_selection` and
  `gvim.lsp.inlay_hints_on/off` → `toggle.inlay_hints_enabled/disabled`). Keys not in the
  map are gvim-only: they have English text, no Fresh translation, and they are absent
  from the translated files on purpose (they fall back to English at runtime).
- `tools/i18n_import.py` regenerates the translated files from
  `refs/fresh/crates/fresh-editor-core/locales/*.json` + the map + `en.json`
  (deterministic sorted JSON). `--check` fails when the committed files are stale. The
  committed files are the build input: `refs/` is only needed to re-run the import.

The package loads English once and each translated file lazily the first time its code
is consulted, so a session that never selects a translated locale pays only for English.
A malformed embedded file panics on first load; the catalogue tests catch that before a
release. `Register` still installs or replaces a table at runtime.

- Placeholders are `%{name}` and are filled from the `vars` map. A placeholder
  with no value is left in the text, so a missing variable shows instead of vanishing.
  Values may be strings, numbers or booleans (the same rendering as the plugin runtime).
- Plurals are one key per CLDR category, suffixed:
  `status.saved_files.one`, `status.saved_files.other`, and also
  `zero`/`two`/`few`/`many` where a language needs them. `TN` fills
  `%{count}` and picks the form by the locale's own rule; a missing form falls back
  to `.other` and then to English.

The English catalogue grows as more app strings move to keys; the translated files are
regenerated from Fresh for the newly mapped keys. A key with no translated value (a
gvim-only key, or a Fresh key a locale leaves untranslated) falls back to English.

## Locale resolution

1. A config locale other than `""` or `auto` wins. It is normalised; an
   unknown code is kept so lookups fall back to English.
2. Otherwise `LC_ALL`, `LC_MESSAGES`, `LANG` in that order.
3. Otherwise English.

Normalisation strips an encoding or modifier (`pt_BR.UTF-8` → `pt-BR`,
`de_DE@euro` → `de`), maps `_` to `-`, matches a known locale, and
otherwise falls back to the primary language subtag (`en_US` → `en`). `C`,
`POSIX` and an empty tag mean English.

Lookup order is the locale, each shorter tag of it (`zh-Hant-CN` → `zh-Hant` →
`zh`), then English, then the key.

## Plurals

`PluralCategory` implements Fresh's CLDR integer rules for the shipped languages:

- English, German, Spanish, Italian, Bulgarian and unknown languages: `one` for 1,
  `other` otherwise.
- French and Portuguese: `one` for 0 and 1, `other` otherwise.
- Czech/Slovak: 1 `one`, 2–4 `few`, else `other`.
- Russian/Ukrainian/Belarusian: 1, 21, 31… `one`; 2–4, 22–24… `few`;
  11–14 and the rest `many` (with `other` as the last-resort form).
- Japanese, Korean, Chinese, Thai, Vietnamese: no grammatical number, always `other`.

No extracted string is count-dependent yet, so the plural forms are not in the shipped
catalogues; `TN`'s per-locale fallback and the category rules are tested with registered
catalogues, and `ValidateCatalogue` rejects a plural form whose category the locale does
not use (for example `.one` in Japanese or `.zero` in Russian).

## Settings row and live apply

Settings → Interface has a `locale` row with `auto` (the default: detect from
the environment) and the 15 Fresh languages. It is a **user-layer** setting: the project
config layer is refused with a diagnostic, because a repository must not choose the user's
UI language (the same rule as the keymap, C11 in `docs/trust.md`). `auto` is
written as Fresh's `null`.

The row is **live**: saving resolves the locale, updates the `i18n` package and the
plugin runtime (`plugin.Runtime.SetLocale`), so `T()`-rendered strings
(status notices, the extracted dock notices, plugin `gvim.i18n.t` and
`gvim.i18n.locale()`) change immediately. It does not rebuild the generated tables:
command titles, palette names and the menu bar come from Fresh's `CommandDef` names
baked at generation time, so they stay English by design (see below). Startup resolves the
locale before the UI and the plugin runtime are built.

## Plugin locale

`gvim.i18n.locale()` returns the editor's locale (the resolved config/environment
locale). `gvim.i18n.t`/`translate` resolve the key through the plugin's own
`<name>.i18n.json` for that locale, then English, then the key, filling
`%{name}` placeholders. `%-prefixed` command titles and descriptions are
translated when the command is registered. The plugin runtime keeps its single-goroutine
contract: `SetLocale` is called on the update loop, and a plugin sees the new locale
at its next call. See `docs/plugins/api-core.md#gvimi18n`.

## Workflow: add a string, translate it, validate

The extracted inventory is the first slice: the editor clipboard statuses
(`clipboard.copied`, `copied_line`, `cut`, `cut_line`, `pasted`, `copied_plain`), the
root notices for the copied path (`clipboard.copied_path`), the buffer formatter
(`format.formatted_with`) and the inlay-hint toggle (`gvim.lsp.inlay_hints_on/off`),
and the dock's user-visible notices (terminal/scrollback notices, gvim's wording),
translated at display time. New strings added by other owners in the same round are
out of scope until they are extracted (see the boundary below).

To extract another string:

1. Find the string in the code and check `refs/fresh/crates/fresh-editor-core/locales/en.json`
   for a key with the same meaning. Same wording → use Fresh's key and add it to
   `i18n/fresh_map.json` (gvim key → Fresh key). gvim's own wording →
   `gvim.<area>.<name>`, keep the current English text, and do *not* map it.
2. Replace the literal with `i18n.T("", key, vars)` (or `TN` for a count) at
   the place it is rendered, so a live locale change is seen; do not freeze the text in a
   package-level `var`. Exported notice constants can become small functions.
3. Add the key and the current English text to `i18n/locales/en.json` (the behaviour
   must not change in English) and add the translated values by running
   `python3 tools/i18n_import.py` (it writes every locale file from Fresh's
   translations; the mapping file decides which keys appear).
4. Run `bash tools/i18n_check.sh` (embedded files validate, the English catalogue is
   complete, mapped keys are translated in all locales, and the committed files match
   Fresh when `refs/` is present) and the string's package tests. Add a rendering test
   with a real embedded locale (for example de) plus the English fallback; no golden files.

If a string has no Fresh translation and should be translated anyway, add it to a
locale file by hand only in a separate translation pass; the import tool regenerates the
mapped files, so translate gvim-only keys in their own follow-up catalogue slice (the
English key and its fallback are already correct).

**What stays English** and is a follow-up inventory: most of the app's inline notices,
prompt/dialog titles and buttons, menu labels and settings labels (settings row names come
from the config keys), the keybinding help text, and anything generated: Fresh's
`CommandDef` command and palette titles (`commands/commands_gen.go`), the
generated menu bar table (`internal/tui/menubar/menu_table_gen.go`), and the hand-written
command rows (for example the terminal-tab palette rows) are data/literals and stay
English until a generator/extraction learns keys.

## Coverage and CI

`i18n.ValidateCatalogue`/`ValidateCatalogueJSON` validate every embedded file against
the English source of truth: unknown keys, the plural key shape and the categories the
locale uses, `%{name}` placeholder sets (a translated value must fill exactly the
English placeholders), duplicate JSON keys, and empty/oversized values. Coverage is
reported per locale by the tests (`TestLocaleCoverage` logs `translated/total` and the
missing list; `CoverageFor` is the programmatic form) and by the import tool.

CI runs `bash tools/i18n_check.sh`:

```sh
go test ./i18n          # embedded files, layout, validation, coverage, fallback
python3 tools/i18n_import.py --check   # when refs/fresh is checked out
```

`i18n/locales/en.json` is the gate: a locale file that validates against it is safe to
ship, and 100% of the mapped subset is enforced for every locale.
